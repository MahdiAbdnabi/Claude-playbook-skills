execution-playbook · how a run works

From a task to a gated, audited build

The skill turns one task into ordered work packages. Each is designed, built tests-first, verified by gate commands and a fresh adversarial reviewer, and closed with a Decision Card. The diagram below is the whole run; the sections after it open each part.

01

Intake and the pre-run questions

Nothing is generated until these are answered. The summary is mandatory and may come from the user, a document, or be suggested backwards from the expected output and confirmed. The expected output is a list of artefacts, each with where it lives and how its existence is checked; that list becomes the top of the definition of done.

Round A — scope and effort

Fastest POCMVPFull
  • Fidelity decides scope, never rigor
  • Effort on Logic · Architecture & Solution Design · UI Design, each Very Low / Recommended / I Am Too Rich
  • Technology suggested first if the task is coding and no stack was named

Round B — execution

Fully AutomatedUser Monitored
  • Output format HTML / MD / Both
  • Cost profile Very Low Budget / Recommended / I Am Too Rich → model tier per stage
  • Tooling: Claude only, or a tool → purpose → WPs map with availability

Round C — checks

Reviewer effort None · Low · Medium · High
  • Each option states its cost per review and what it misses
  • Build self-check Minimal / Standard / Tool-backed
  • Extra review lenses on top of Correctness, Security, Maintainability, Operability

The run then reads the whole configuration back in one block, generates the tracker and the usage guide, and only then starts Phase 0.

03

Guards: what each shortcut is not allowed to hide

Every cost-saving rule in the loop carries a mechanical check, so a cheaper run cannot pass as a thorough one.

RuleWhat it savesGuard
Context packsHelpers stop loading 150–360k tokens of reading listEverything quoted carries [src:]; an on-demand read list; a helper that needs more raises [GAP] instead of roaming; packs stamped with the commit and marked stale if a quoted file changed
Mutation harnessOne call instead of edit / run / restore per mutantBaseline must pass in the private copy; a known-killed and a known-survivor sentinel fail the harness on mismatch; environment guards can never be removal candidates
One gate runBuilder, coordinator and reviewer no longer each re-run five minutes of testsLog stamped with the tree hash; the reviewer's first action is gate.py --verify; a mismatch is Blocking
Call capsShorter conversations, fewer re-readsStopping at the cap with a clean handoff is a correct outcome; the cap never skips the sweep or the gate; a hit raises a card (continue +N · split · stop)
Fix by continuationNo fresh fix helper reloading the projectOnly while the builder's conversation is cached and under the size threshold; findings enter as facts; a weakened test is Blocking at re-review
Scoped re-reviewSecond reviews cost a fraction of the firstEscalates to a full review when the diff leaves the fence, touches a quoted contract or a test's assertions, exceeds a third of the WP, a prior High was on Security/Compliance/Domain, the WP is [PROTECTED], it is attempt 3, or the reviewer sees a new High outside the diff
Reviewer effort levelsLow and Medium cost 5–30k per review instead of 80–360kNone marks every gate and is listed by Phase 5; after the pilot the actual tokens and findings are read back next to the chosen level

Rigor is never on the dial. Fidelity, effort, cost profile, reviewer effort and self-check change how much is in scope and how hard it is checked; they never change that tests come first, the reviewer is fresh, gaps are tagged, and a gate is never weakened for what is in scope.

04

Who runs what, and on which model

The agent that invoked the skill is the orchestrator. It launches a separate agent per stage with the model and effort resolved from the cost profile, collects findings and tags, logs calls and tokens, and raises Decision Cards. It never builds, reviews or re-runs a gate whose hash matches.

05

What a run leaves behind

Records

  • PLAYBOOK.md goal, definition of done, locked decisions, WP breakdown
  • work-packages/WP-NN.md ACs, test list, fail-first evidence, mutation table, gate history
  • decisions/DC-###.md every card with its evidence and outcome
  • adr/, DECISIONS.md, GAPS.md, RISKS.md

Evidence

  • logs/WP-NN-gate-n.json structured gate summaries with tree hash
  • logs/WP-NN-mutation.md harness tables
  • review/WP-NN-review-n.md findings per attempt, scoped or full
  • packs/ what each helper was actually given

Measurement

  • First-review pass rate (baseline run: 1 of 7)
  • Calls per stage against the cap; cap hits
  • Review tokens first → re-review; scoped vs full
  • Mutants listed / survived; fixes continued vs fresh

The tracker's "Next action" line and the usage guide are what a returning person or a fresh session reads first. Answering an open card is one line: DC-007: B — keep the dispatcher hand-rolled.

Tags used throughout: [src:] [GAP] [ADR-###] [DC-###] · Phase 5 remains a fresh, full pass over the whole run, so anything a scoped review missed still has a backstop.
