documentation-playbook · how a run works

From a codebase to a traceable, audited corpus

The skill documents an existing system in batches of modules. Every claim carries its evidence tag, every extraction phase ends with a mechanical check, a fresh auditor samples the citations, and the pilot batch proves the shape before the rest is scaled. The diagram below is the whole run; the sections after it open each part.

01

Intake and the pre-run questions

Both intake inputs are optional: a summary of the system's business and technical shape, and how to reach the target (repository, folder, running environment). Everything the summary says is treated as a claim to verify, not a fact. Three question rounds follow, and nothing is generated until they are answered.

Round 1 — how the run executes

Fully AutomatedUser Monitored
  • Output format HTML / MD / Both (Markdown is always authored; HTML is rendered from it)
  • Cost profile Very Low Budget / Recommended / I Am Too Rich → model tier per phase
  • Lenses: Architect, Developer, QA, BA always; OPS, SEC, DATA, PO, SUP, INTG, MIG, AUD on request

Round 2 — output profile

Full30-min read10-min read
  • Content: documents + diagrams, documents only, diagrams only
  • Diagram style: static Mermaid, interactive page (HTML only), none
  • Diagram depth: high-level design, design, full tracking (D1–D10)

Round 3 — checking

Audit effort None · Low · Medium · High
  • None: doc_check only, every batch marked unaudited
  • Low: citation sample only (~5–10k per audit)
  • Medium: auditor pack + 5 falsifications (~15–40k)
  • High: whole corpus and repository (~80–300k)

The run reads the configuration back in one block, generates the tracker and the usage guide, and only then starts Phase 0.

03

Guards: what each shortcut is not allowed to hide

Every cost-saving rule carries a mechanical check, so a cheaper or shorter run cannot pass as a thorough one — and a document never sounds more certain than its evidence.

RuleWhat it savesGuard
Evidence tagsNo re-reading to find out what is provenEvery non-trivial claim is [src: File#Member], [GAP], [DRIFT], [PLANNED] or [UNTESTED]; hedging words are forbidden — evidence or a gap, never "probably"
Pilot firstA wrong taxonomy is found on one batch, not sevenThe pilot's audit closes with a Decision Card: scale, adjust the document shape, or re-pilot; nothing else starts before it
Context packsExtractors stop loading the whole repository and corpusShared block hashed and placed first for caching; packs stamped with the commit, quoted files marked [STALE] if changed; a helper that needs more raises a gap instead of roaming; the auditor's pack is built from the corpus and the check, never from the extractor's
Mechanical checkThe auditor no longer spends its budget on broken citationsdoc_check.py after every extraction phase: every citation resolves to file#member, GAP/DRIFT ids reconcile with the logs, [rule: TBD] is zero after Phase 3, every [PROTECTED] has a status, every diagram element is tagged; a blocking report does not close the checkpoint
One check per phaseNo re-runs by the orchestrator or the auditorReport stamped with the code's tree hash; the auditor's first action is to confirm the hash still matches; a mismatch means the corpus describes different code
Call capsShorter conversations, fewer re-readsCaps per phase by depth; stopping at the cap with documents saved and a done / left / next note is a correct outcome; the cap never skips the check; a hit raises a card
Fix by continuationNo fresh fix helper reloading the batchOnly while the extractor's conversation is cached and under the token threshold; misses enter as facts; deleting a claim without a gap is a finding at re-audit
Scoped re-auditSecond audits cost a fraction of the firstEscalates to a full audit at the audit tier when a miss was on a [PROTECTED] rule, more than a third of the batch's documents changed, or it is attempt 3
Audit effort levelsLow and Medium cost 5–40k per audit instead of 80–300kNone marks every batch unaudited in the tracker and the index; after the pilot the actual tokens and misses are read back next to the chosen level

Rigor is never on the dial. Depth, content mode, diagram depth, cost profile and audit effort change how much is written and how hard it is checked; they never change that claims carry evidence, the auditor is fresh, gaps are logged instead of guessed, and a [PROTECTED] invariant is never silently rewritten.

04

Who runs what, and on which model

The agent that invoked the skill is the orchestrator. It launches a separate agent per phase and batch with the model and effort resolved from the cost profile, runs independent batches concurrently, takes GAP and DRIFT entries back into the tracker, and raises Decision Cards. It never extracts, and the Phase 5 auditor is always an agent that did not write the corpus.

Records

  • _playbook/TRACKER.md run config, phase × batch matrix, GAP / DRIFT / decision logs, next action
  • decisions/DC-###.md every card with its evidence and outcome
  • lenses/ one entry page per role
  • diagrams/ Mermaid blocks or the interactive page

Evidence

  • logs/check-n.json mechanical check per phase, tree-hashed
  • logs/sample-n.json the citations the auditor saw, with the code
  • logs/audit-n-misses.json what was wrong, what the code says
  • packs/ what each helper was actually given

Measurement

  • Citation hit rate first audit → re-audit; scoped vs full
  • Calls per phase against the cap; cap hits
  • Unresolved citations and hedges caught before the auditor
  • Open gaps by severity; drift on protected invariants

The tracker's "Next action" line and the usage guide are what a returning person or a fresh session reads first. When the code changes later, a delta round marks affected citations [STALE] and re-runs only the phases that touch the changed modules.

Tags used throughout: [src:] [GAP] [DRIFT] [PLANNED] [UNTESTED] [PROTECTED] [DC-###] · Phase 6 packages a corpus the audit has already verified, so the AI knowledge base inherits the evidence trail rather than restating it.
