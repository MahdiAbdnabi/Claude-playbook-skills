# Execution Playbook

Turns a task into **ordered work packages**, each built **tests first**, verified by **gate commands** and an **adversarial review in a fresh context**, with a **Decision Card** at every phase boundary so the person (or, unattended, a fixed rule set) decides what happens next with the evidence in front of them. The playbook exists because an AI agent will happily keep building on its own mistakes; the gates decide *when to stop and check*, the tags show *what is proven*, the ADRs and Decision Cards record *why a choice was made* — while the answer is still known.

`references/playbook-core.md` is the methodology (principles, tags, phases with prompts, gates, decision rules, model guide, resuming). `references/review-lenses.md` is the reviewer-perspective catalog. `references/decision-cards.md` is the card format and when one is mandatory. `references/cost-and-orchestration.md` defines the cost profiles and how the orchestrator launches stage agents with different models and efforts. `references/intake-and-fidelity.md` defines the mandatory summary and expected output, technology suggestion, the three fidelity levels, the three effort dimensions, and the tooling plan. `references/review-depth.md` defines the reviewer-effort levels and the context packs helpers are briefed with. `references/self-check.md` defines the Build self-check levels, the mutation sweep, control tests and the derived test budget. `references/step-budgets.md` defines per-stage call caps, the gate and mutation scripts, summaries-not-logs, and one-gate-run-per-stage with its guards. Read all eight before Phase 0 of any run. Everything below is how **this skill** runs the playbook.

## 1. Intake — summary, expected output, access (definitions in `references/intake-and-fidelity.md`)

Three things are settled before any question about *how* to run. Take what the conversation already holds and confirm it in one line rather than re-asking.

| Input | Required | Sources | If absent |
|---|---|---|---|
| **Task summary** — business half (what, for whom, why now, what done looks like) and technical half (stack, constraints, locked decisions, non-goals, integrations) | **Yes** | Any combination of: the user's description; a document (attached spec, issue, design doc, file in the connected folder — read it and summarise with `[src: DOC §n]`); or **suggested by Claude from the expected output** when the user only describes the result they want. Record which in `summary_sources`. | Draft it from the expected output and any document, read it back, and get a one-line confirmation. Nothing starts on an unconfirmed summary. Unstated constraints are `[GAP]`s, never defaults. |
| **Expected output** — the observable artefacts the run must produce, each with *where it lives* and *how its existence is checked* | **Yes** | The user; the summary; the document. | Ask once, with a proposed list derived from the summary. An output that cannot be checked is a `[GAP]` and blocks Phase 0 — a run that cannot tell when it is finished cannot be gated. |
| **How to reach the target** — connected folder, repo, empty folder to create in, Cowork project, connectors | Yes | Look first: connected folders, attachments, repos in session. | Ask once; if still nothing, stop — the playbook cannot verify work it cannot run. |

A summary is **intent, not evidence**: acceptance criteria are still met by tests and gates, and where the summary conflicts with a spec or existing code, log `[DRIFT]` and raise a Decision Card — never pick silently. The expected output becomes the top of the definition of done; Phase 5 traces every item of it to an acceptance criterion and a passing test.

**Technology suggestion (coding tasks).** If the task is coding and neither the summary nor the expected output names the technologies, propose them before Phase 0 with `AskUserQuestion`: one recommended set (language/runtime, framework, storage, test tooling, build/run — one line each on why it fits this task at the chosen fidelity) plus one or two alternatives. What is already in the target repo is the default recommendation; a Fastest POC gets the fewest moving parts that can show the logic; stated constraints (offline, licensing, team familiarity, a parent programme's locked stack) are honoured. The answer becomes locked decisions. Skip this entirely when the user already named the stack.

## 2. Pre-run questions — ask before anything is generated

Use `AskUserQuestion` when available, in three rounds of up to four (plain text otherwise). Nothing is generated before the answers. Round A settles **what is being built and how good it must be**; round B **how the run executes**; round C **how hard the reviewer and the builder's own checks work**.

### Round A — scope and effort (rules in `references/intake-and-fidelity.md §4–5`)

**A1 — Fidelity level**
- **Fastest POC** — make the happy scenario work at the least cost: cheapest viable technology, the simplest code design and architecture, no validations beyond what the path needs to execute. One smoke test per WP, reviewer on CORRECTNESS (happy path) only, 1–3 WPs, everything skipped listed once as `[PLANNED]`, every artefact labelled POC.
- **MVP** — a working vertical slice a user can exercise end to end, with good architecture and solution design kept, and the main validations applied (boundary input validation, authorization gates, user-facing error paths, the invariants the slice touches). Full gates, default lenses.
- **Full implementation** — ready and tested, considering the best approaches: non-functional ACs written and tested, all selected lenses at full depth, complete handover, Phase 5 with citation sample.

Fidelity is a scope decision, not a rigor decision: tests still come first, the reviewer is still fresh, gaps are still tagged, gates are never weakened. Moving up later is a delta round that re-opens the `[PLANNED]` items.

**A2 — Effort on Logic · A3 — Effort on Architecture & Solution Design · A4 — Effort on UI Design**, each **Very Low · Recommended · I Am Too Rich** (defaults: Recommended; a Fastest POC defaults all three to Very Low; UI is "n/a" when there is no interface). Logic ranges from "exactly the stated rules" through "ACs plus the edge cases they imply" to "exhaustive, property-based, invariants verified". Architecture ranges from "simplest structure, no ADRs beyond locked decisions" through "layered to conventions, ADR per non-obvious choice" to "C4 + options analysis + NFR review per WP". UI ranges from "functional and unstyled" through "consistent, accessible basics, all states" to "a design pass with the `frontend-design` skill before Build, polished, UX-lens reviewed". The cost profile (B3) picks the model; effort allocation picks how much work that model is asked to do in each area — and a dimension at I Am Too Rich under a Very Low Budget profile runs its stages at the Recommended tier instead.

### Round B — execution

**B1 — Execution mode**
- **Fully Automated** — Claude runs every work package end to end: builds, runs gates, spawns the reviewer, applies fix loops, and resolves each Decision Card itself using the decision rules (`playbook-core.md §7`), recording the rule used. It stops only for: a `BLOCKED` work package (gate cannot pass without inventing or weakening it), an irreversible action with a real either-way choice (destructive migration, deleting data, publishing), or a Decision Card whose options differ in cost by more than the run's stated budget.
- **User Monitored** — the user manages prompt execution. Claude prepares each phase prompt for the current work package, runs it on the user's go (or the user runs it in their own Claude Code / Cowork session and reports back), stops at every gate with the Decision Card, and waits. The tracker records who ran what.

**B2 — Output format** for the playbook artefacts (tracker, usage guide, decision cards, ADRs, reviews): **HTML**, **MD**, or **Both**. Markdown is always authored (it is what lives in the repo and what later sessions read); HTML is rendered from it with `scripts/render_html.py`. "HTML only" still keeps the Markdown in `_playbook/src/` — say so in one line.

**B3 — Execution cost profile** (resolution rules in `references/cost-and-orchestration.md`):
- **Very Low Budget** — Haiku does most of the work: every phase drops two model tiers and one effort step, except the critical phases (adversarial review, final audit, and Design of WPs that touch protected or irreversible areas), which floor at Sonnet so a gate is still a real check.
- **Recommended** (default) — the playbook's per-phase guide: the most efficient model for each phase at the most efficient effort. Builds stay on Sonnet; reviews and audits get Opus.
- **I Am Too Rich** — always one cost level above recommended: one model tier up for every phase, one effort step up where a phase is already on the top tier.

Record it in the config (`cost_profile`), regenerate the tracker, and read back the resolved table in one line before Phase 0. Switching mid-run applies to stages not yet started and is logged as a decision. The cost guard (`cost-and-orchestration.md §3`) raises a Decision Card when a stage exceeds twice its budget, regardless of mode.

**B4 — Tooling**: is **Claude the only tool** executing the task, or are **other tools and integrations expected**? If others: name the mapping — each tool, skill, MCP server or connector, what it is used for, in which WPs, what it produces (for example, the PixelLab MCP for the 2D sprites and tilesets of a game, the `frontend-design` skill for a UI pass, a CI system for gate commands, a database connector for seed data). The user names what they know; Claude proposes the rest from what the expected output needs, checks each entry's availability in the session (`available` / `needs-setup` / `missing`), and records the list in `tooling`. Each WP Design then names the tool for every output produced that way, and its gate checks the produced artefact like any other. A tool that turns out missing at Build time is a `[GAP]` and a Decision Card — set up, substitute (named), or defer `[PLANNED]` — never a silent hand-made replacement. "Claude only" is recorded too, so a later session does not reach for an excluded tool.

### Round C — reviewer effort (rules, cost figures and the pack mechanism in `references/review-depth.md`)

**C1 — Reviewer effort**: how the adversarial reviewer is briefed and how far it looks. State the cost and the effect with each option — the trade is real both ways:
- **None** — no independent review; gates are commands + the builder's self-check. ~0 extra cost. Gates stop catching confident-but-wrong builds; every gate is marked `review: none` and Phase 5 lists them. POC or throwaway spike only — warn once if chosen with MVP or Full.
- **Low** — reviewer sees the ACs, the diff, the gate output and the lens checks. ~5–10k input tokens per review. Catches untested ACs and diff-level errors; cannot see anything outside the diff (a contract broken elsewhere, a duplicated rule).
- **Medium** (recommended; default for MVP and Full) — reviewer gets a **context pack**: a fixed shared block (cached across launches) then ACs, the contracts the WP touches quoted with `[src:]`, the ADRs it depends on, the diff, the builder's least-sure items as hints, and an on-demand read list. ~15–30k per review, the shared part at cached-read price. Catches most of what full reading catches; misses what the coordinator did not select — the pilot shape check asks whether the reviewer lacked anything.
- **High** — full reading, the previous default: the pack plus PLAYBOOK.md, CLAUDE.md, every ADR, earlier WPs and reviews, the whole repo. ~80–360k per review. Finds the convention nobody quoted and the finding that recurs; can cost more than the build it reviews.

Defaults: Low for a Fastest POC, Medium otherwise; High is chosen, never assumed. Record as `review_depth`. It multiplies with the cost profile (High × I Am Too Rich is the most expensive combination the skill offers — say so if both are chosen). After the pilot WP, read back the pilot review's actual tokens and findings next to the chosen level and offer to change it for the remaining WPs; mid-run changes apply to stages not yet started and are logged as decisions.

**C2 — Build self-check** (rules in `references/self-check.md`): what the builder does to its own tests before reporting, so the reviewer stops finding "no test could catch this".
- **Minimal** — fail-first evidence only (the failing run pasted into the WP file before the code is written). ~0 extra. Expect most first reviews to fail on untestable guards and detectors. Default for a Fastest POC.
- **Standard** (recommended; default for MVP and Full) — fail-first + a **mutation sweep** (list every conditional, boundary, fallback, call order and cap the WP added; mutate each; a survivor gets a test — or a static unreachability argument, never for environment guards; restore verified by a gate command) + **control tests** for every detector through the real path + the mutation table in the WP file. Roughly +20–40% on Build; typically less than one fix loop and re-review.
- **Tool-backed** — Standard + a mutation-testing tool for the stack (Stryker, mutmut, PIT, cargo-mutants) set up in WP-00 and run per gate on the changed files with a kill-rate threshold. Slower gates; most objective. Choose for Full fidelity or WPs touching `[PROTECTED]` rules.

Record as `self_check`. The reviewer re-applies three mutants from every table, so the sweep is checked, not trusted; and the self-check never lowers reviewer effort — it removes the mechanical class of findings, not the conceptual one. The **test budget** is not asked: it is derived from fidelity and Logic effort (`self-check.md §4`), Design plans against it, and exceeding it raises a Decision Card (approve / trim / split the WP). The tracker shows the run's **first-review pass rate**, which is the number this option exists to move.

**C3 (optional) — Additional review lenses**: the four defaults (CORRECTNESS, SECURITY, MAINTAINABILITY, OPERABILITY) always apply to the adversarial reviewer (Fastest POC narrows this to CORRECTNESS, happy path). Offer the optional catalog from `references/review-lenses.md` as a multi-select, defaulting to none. A lens the user names that is not in the catalog is fine — define it with the same checks/entry-points shape in the config.

Settle silently from context: **output location** (`_playbook/` inside the target repo if writable, else a `playbook-<task>/` folder in the workspace); whether a **previous run** exists there (then resume — §6 — not a fresh run); and the **gate toolchain** (what test/lint/build commands exist, or need creating in WP-00).

Before Phase 0, read the whole configuration back in one short block — summary sources, expected outputs, stack, fidelity, the three effort levels, mode, format, cost profile with the resolved model table, tooling — reviewer effort with its estimated cost per review, self-check level and the derived test budget — so the user can correct any of it in one line.

## 3. Generate the tracker and the usage guide first

Before Phase 0, produce and show:

1. **Execution tracker** — `scripts/build_tracker.py` from `_playbook/run-config.json` (schema in the script header). Writes `TRACKER.md`/`.html`. It holds: run config (mode, format, cost profile, lenses, locked decisions, decision rules, and per phase the recommended / resolved / actually-used model and effort), the **work package × stage matrix** (Design / Build / Verify / Gate), gate results with fix-loop counts, the **Decision Card register**, ADR log, GAP/DRIFT logs, risk register, session log, and a **"next action"** line naming the exact next prompt. The config is the single source of truth; `STATE` lives inside it; the tracker is a view — regenerate after every stage.
2. **Short usage guide** — `USAGE.md`/`.html` from the same script: what the run produces, how to read a tag, how to answer a Decision Card, how to unblock a BLOCKED package, how to resume, how to switch mode.

Phase 0 fills in the work packages, so the first build has `work_packages: []`; regenerate after Phase 0 and after every stage change.

## 4. Running the phases

Follow `references/playbook-core.md §6`. Rules that hold in both modes:

- **Frame before building.** Phase 0 takes the confirmed summary, the expected outputs, the stack, the fidelity level, the effort allocation and the tooling plan, and produces the goal statement, the definition of done (expected outputs first), locked decisions, non-goals, constraints, the work-package breakdown with dependencies sized to the fidelity (1–3 WPs for a POC), the gate toolchain, the per-WP tool assignments, and a pilot WP. It ends with **DC-000**, the first Decision Card: approve the breakdown or change it. Nothing is built before DC-000 is decided.
- **Fidelity and effort shape every stage.** Design, Build and Verify read the fidelity level and the three effort levels from the config (`intake-and-fidelity.md §4–5`) and do that much: a POC Build writes the happy path and one smoke test and lists what it skipped as `[PLANNED]`; an MVP Build applies the main validations; a Full Build adds the non-functional ACs. A UI effort of I Am Too Rich inserts a design pass (the `frontend-design` skill) before the Build of any UI-bearing WP. The reviewer's lens set follows the fidelity (CORRECTNESS-only for a POC). None of this lowers the gate for what *is* in scope.
- **Pilot first.** Run the pilot WP through Design → Build → Verify → Decision Card before any other. After it, do the shape check (`playbook-core.md §9.1`): were the acceptance criteria testable, did the reviewer find real issues, did the gate catch what the self-check missed? Fix the pattern before scaling.
- **Tests before code, then teeth.** Build starts by writing the acceptance tests from the Design's criteria; they must fail first for the right reason, and the failing run is pasted into the WP file as evidence. A WP whose criteria cannot be expressed as a test gets a `[GAP]` and a Decision Card, not a skipped test. At Standard or Tool-backed self-check, Build ends with the mutation sweep (`self-check.md §2`): every conditional, boundary, fallback, call order and cap the WP added is mutated, a survivor gets a test (code is removed only on a written static argument and never for environment guards), the restore is proven by a gate command, every detector has a control test through the real path, and the mutation table goes in the WP file for the reviewer to re-apply. Design plans tests against the derived budget and raises a Decision Card when it exceeds it.
- **Helpers get a pack, not a reading list.** Before launching a Build or Verify stage, run `scripts/build_context_pack.py WP-NN` to produce three files: `packs/shared.md` (immutable for the run, byte-identical on every launch, hashed — placed **first** in every helper prompt so prompt caching reuses it), `packs/WP-NN-builder.md` (ACs, quoted contracts, dependent ADRs, open gaps, tool assignments, the files it may change, the files it may read on demand, the ids it may allocate) and `packs/WP-NN-reviewer.md` (sized by the reviewer effort, built from the WP file, diff and gate log — never from the builder's block). Packs are built at launch time, stamped with the commit they were built from, and a quoted file that changed before collect marks the result `[STALE]` and re-launches. A helper that needs something outside its pack raises a `[GAP]`; it does not roam. Phase 5 is exempt and reads everything. Full rules: `references/review-depth.md §2`.
- **Steps are budgeted; scripts do the repetitive ones.** Every launch carries the stage's tool-call cap from `budget.calls` (scaled by fidelity, `references/step-budgets.md §3`), enforced with `max-turns` where the tool offers it. Stopping at the cap with a clean handoff (compiles, nothing committed, done / left / next in the WP file) is a correct outcome; the orchestrator then raises a Decision Card — continue +N, split the WP, stop. Build runs the gate **once** through `scripts/gate.py`, which writes the full log plus a structured summary stamped with the tree hash; helpers read the summary (`--show`) and open the log only at a failing command's offset. The mutation sweep runs through `scripts/mutate.py` (private worktree per mutant, sentinels that fail the harness if its results are wrong, full-suite re-run before calling anything a survivor); the builder writes the mutant list and reads the table. The reviewer's first action is `gate.py --verify`: a tree-hash mismatch is a Blocking finding; it re-runs the gate only on the named triggers. Nobody else re-runs a gate whose hash matches.
- **The orchestrator launches, it does not build.** The agent running this skill is the orchestrator: it resolves the per-phase model/effort table for the chosen cost profile, then delegates each stage of each WP to a subagent via `Agent` with `model` and `effort` set from that table — so a single run can have Haiku doing integration bookkeeping, Sonnet building, and Opus or Fable reviewing and auditing, each stage on the model the playbook recommends for it. Give the subagent its pack (shared block first, then its own block), the filled stage prompt and the output paths; launch independent WPs at the same stage concurrently; take back findings, GAP/DRIFT/ADR entries and card requests into the config; log every launch (phase, WP, model, effort, outcome) so the tracker's "actually used" column is true. The **reviewer and the auditor are always fresh agents** — never the builder's context, never a continuation — given the code, the acceptance criteria, the active lenses, and nothing of the builder's reasoning. If `Agent` is unavailable, run stages yourself in sequence, lean on effort, and run the review as a separate pass after discarding working notes, marked `self-review` in the tracker so the weaker guarantee is visible. Full rules: `references/cost-and-orchestration.md §3`.
- **Gates are not negotiable.** A gate's commands and the reviewer's verdict decide PASS/FAIL. On FAIL, the fix **continues the builder's conversation** with the findings as facts (a finding stands unless the fixer shows a test proving it wrong) while that conversation is still cached and under the size threshold — otherwise a fresh fix helper with the pack — then one gate run and a **scoped re-review** by a fresh reviewer: it re-applies each prior finding's mutant, diffs the tests (any weakening is Blocking), re-applies mutants added since, and checks the diff under the lenses; `build_context_pack.py --scoped` escalates to a full review when the diff leaves the fence, touches a quoted contract or a test file, exceeds a third of the WP's files, a prior finding was High on SECURITY/COMPLIANCE/DOMAIN, the WP touches `[PROTECTED]`, or this is attempt 3. Max 2 fix loops. Then the WP is `BLOCKED`, the run stops at a Decision Card with the findings, and nothing downstream starts. Never weaken a gate, delete a failing test, or lower a threshold to pass — if a threshold is wrong, that is an ADR + Decision Card, not a quiet edit.
- **Gaps are truth.** Missing facts become `[GAP]` entries with a one-line question; the build continues on what is known. Invented defaults are the most common way an unattended run degrades — a `[GAP]` is cheaper than a wrong assumption discovered three WPs later.
- **Decision Cards between phases.** One at every phase boundary of every WP (Design→Build, Build→Verify is implicit in the gate, Verify→next WP) and whenever an ADR-level choice appears mid-stage. Format and mandatory triggers: `references/decision-cards.md`. In User Monitored mode the run waits on the card. In Fully Automated mode the card is resolved by the decision rules, marked `AUTO-DECIDED` with the rule number, and the run continues — but a card whose options are irreversible or exceed budget stops the run regardless of mode.
- **Record while you still know why.** Every non-obvious technical choice gets an `ADR-###` (template in `playbook-core.md §10.2`) at the gate, tagged like everything else. Every decision (card or rule-driven) lands in `DECISIONS.md`. Every unknown in `GAPS.md`. These three files plus the tracker are what a returning person reads.
- **Commit per passed WP** when the target is a git repo: `WP-NN: <name> (PASS)`, after the gate and review, never before.

## 5. Finishing a run

Deliver in this order: the one-line result (WPs passed / blocked, gate pass rate, open Decision Cards, open Blocking/High gaps), the tracker, the usage guide, then the open Decision Cards and gap questions as a numbered list the person can answer in place. No phase recap. If output lives in a connected folder, say where; otherwise send the files (zip if more than ~10).

Offer one next step only: answering the open cards (which resumes the run), or scheduling the next run when the spec changes.

## 6. Resuming or updating a run

On "continue", "where were we", "unblock WP-04", "the spec changed": read `_playbook/run-config.json` and the tracker first, then:
- unfinished → resume at "next action" in the recorded mode; ask only if they want to switch;
- answered Decision Cards → apply the decision, update `DECISIONS.md`, regenerate the tracker, continue;
- `BLOCKED` WP with new input → re-enter at the fix session with the fix counter reset to 0 and the new input recorded on the card;
- changed spec → a **delta round** (`playbook-core.md §9.3`): diff the spec, mark affected acceptance criteria `[STALE]`, re-run Design on affected WPs, re-run gates on everything downstream of them.

## Files in this skill

- `references/playbook-core.md` — principles, tags, work-package anatomy, the phases with prompts, gates, decision rules for unattended runs, model/effort guide, runner notes, resuming and delta rounds, templates (WP file, ADR, reviewer prompt, DECISIONS/GAPS entries).
- `references/review-lenses.md` — default and optional reviewer lenses and how to define a custom one.
- `references/decision-cards.md` — the Decision Card format, mandatory triggers, how automated mode resolves them.
- `references/cost-and-orchestration.md` — the model/effort ladders, the three cost profiles and their resolution rules, the orchestrator's launch/collect/record loop, and the cost guard.
- `references/review-depth.md` — the four reviewer-effort levels with cost and effect, the context-pack mechanism (shared cached block, builder block, reviewer block), staleness stamps, budgets, exemptions.
- `references/self-check.md` — self-check levels (Minimal / Standard / Tool-backed) with cost and effect, the mutation sweep with its safety rules, detector control tests, the derived test budget, reviewer and audit hooks.
- `references/step-budgets.md` — per-stage tool-call budgets with the consistent-stop rule, the mutation harness with sentinels, structured gate summaries, one gate run per stage bound to a tree hash.
- `references/intake-and-fidelity.md` — summary sources, expected-output format, technology suggestion rules, fidelity levels (Fastest POC / MVP / Full) and what each changes, effort allocation on Logic / Architecture & Solution Design / UI Design, and the tooling plan.
- `scripts/build_tracker.py` — run-config JSON → `TRACKER.md/.html` + `USAGE.md/.html`. `python3 scripts/build_tracker.py --help`.
- `scripts/gate.py` — runs a WP's gate commands once; writes `logs/WP-NN-gate-<n>.log` + `.json` summary (per command exit, duration, counts, first failure, offset) stamped with the tree hash; `--show` for helpers, `--verify` for the reviewer.
- `scripts/mutate.py` — mutation harness: mutant list in, private worktree per mutant, sentinels, full-suite re-run on survivors, table out to `logs/WP-NN-mutation.md`.
- `scripts/build_context_pack.py` — builds `packs/shared.md` (hashed, cache prefix), `packs/WP-NN-builder.md` and `packs/WP-NN-reviewer.md` for one launch, from the config, CLAUDE.md, the WP file, ADRs and git. Prints token estimates. `--help` for options.
- `scripts/build_decision_card.py` — card JSON → `decisions/DC-###.md/.html`, and appends the card to the run config register. `--help` for the schema.
- `scripts/render_html.py` — renders every Markdown file under `_playbook/` (work packages, decisions, ADRs, reviews) to HTML with a sidebar index and tag highlighting. Needs `pip install markdown`.
- `assets/run-config.example.json`, `assets/decision-card.example.json` — filled examples to copy from.
